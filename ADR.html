ADR-001: Микросервисная архитектура

Статус: Принято

Дата: 09.12.2025

Участники: Техлид бэкенда

Контекст

Платформа объединяет разнородные функции с разными требованиями к нагрузке: интерактивный редактор (требует <300мс задержки), генерация диаграмм (ресурсоемкие ML-запросы), система оценки качества (вычислительно сложная), управление проектами (CRUD-операции). Монолитная архитектура не позволит независимо масштабировать компоненты.

Решение

Разделить систему на семь микросервисов с API Gateway и выделенным Backend-for-Frontend для веб-клиента. Каждый сервис развертывается независимо в Docker-контейнерах, оркестрируется через Kubernetes. Межсервисное взаимодействие: синхронное через HTTP/REST, асинхронное через RabbitMQ (см. ADR-003). BFF-сервис агрегирует данные от нескольких бэкенд-сервисов для уменьшения количества запросов с клиента.

Конкретные сервисы:

  • Bff-gateway. Единая точка входа, аутентификация, маршрутизация;
  • User-service. Управление пользователями, проектами, правами доступа;
  • Diagram-service. Бизнес-логика редактора, хранение диаграмм в MongoDb;
  • Generation-service. Очередь задач генерации, интеграция с ML;
  • Ai-assistant-service. Анализ диаграмм, генерация рекомендаций;
  • Export-service. Рендеринг в PNG/SVG через headless Chrome;
  • Layout-service. Оценка качества компоновки по 5 метрикам.

Последствия

Положительные: Независимое развертывание (можно обновлять генератор без остановки редактора)

Отрицательные: увеличение операционных затрат в 2-3 раза, необходимость реализации распределенной трассировки для отладки.

ADR-002: Фронтенд на React 18 с React Flow и Vite

Статус: Принято

Дата: 09.12.2025

Участники: Техлид фронтенда

Контекст

Требуется создать сложный интерактивный редактор диаграмм с откликом <300мс и поддержкой совместного редактирования. ТЗ ограничивает выбор React 18 (п. 4.6).

Решение

Использовать связку React 18 + TypeScript + Vite + React Flow. React Flow выбран как наиболее зрелая библиотека для построения редакторов графов в React-экосистеме. Для состояния редактора использовать Zustand. Для реального времени Socket.io-client. Сборка через Vite для быстрого hot-reload.

React Flow с кастомными узлами для элементов диаграмм, Zustand-стор с селекторами для вычисляемых метрик качества, virtualized список элементов палитры для диаграмм с 200+ элементов и добавление дебаунсинга изменений диаграммы (500мс) перед отправкой на оценку качества.

Последствия

Положительные: Скорость разработки UI увеличивается на 30% за счет готовых компонентов React Flow, TypeScript снижает количество runtime-ошибок.

Отрицательные: Требуется кастомная адаптация формата данных от ML-сервисов.

ADR-003: Асинхронная обработка ML-запросов через RabbitMQ

Статус: Принято

Дата: 09.12.2025

Участники: ML-инженер

Контекст

Операции генерации диаграмм, оценки компоновки и работы AI-помощника требуют вызова ресурсоемких ML-моделей, время выполнения которых может превышать стандартные HTTP-таймауты. Необходимо обеспечить время генерации не более 30 секунд для 95% запросов, при этом клиент не должен блокироваться в ожидании.

Решение

Для асинхронной обработки ML-запросов использовать брокер сообщений RabbitMQ с паттерном “Task Queue”.

Сервис для генерации диаграмм создает сообщение-задач с уникальным task id и помещает его в очередь ml_generation_queue. Пул воркеров на Python забирает задачи из очереди, выполняет синхронный вызов внешнего ML-сервиса через gRPC, затем публикует результат в очередь ответов results queue, ключом является task id. Результат кешируется в Redis на 5 минут. Клиент через WebSocket запрашивает результат по task id.

Благодаря поддержки подтверждений доставки RabbitMQ гарантирует, что задача не потеряется при падении воркера, встроенные механизмы retry и dead letter queues позволяют обрабатывать сбои ML-сервисов, а управляемая персистентность сообщений сохраняет задачи при перезапуске брокера.

Последствия

Положительные: Устойчивость к долгим ML-запросам, возможность горизонтального масштабирования воркеров, отказоустойчивость.

Отрицательные: Усложнение инфраструктуры (необходимость мониторинга очередей), дополнительная задаржка на сериализацию сообщений (~50-100 мс).

ADR-004: Хранение данных: PostgreSQL для метаданных, MongoDB для диаграмм, Redis для сессий, S3 для файлов

Статус: Принято

Дата: 09.12.2025

Участники: Разработчик БД

Контекст

Система управляет разнородными данными: структурированными метаданными (пользователи, проекты, права доступа), полуструктурированными данными диаграмм (графы с изменяемой схемой), сессиями и файлами экспорта. Единая СУБД не подходит для всех сценариев. Решение Использовать комбинацию из четырех специализированных хранилищ: PostgreSQL для структурированных данных, MongoDB для данных диаграмм, Redis для оперативных данных (Кэш результатов ML-обработки, JWT, refresh токены) и S3-совместимое хранилище для файлов.

PostgreSQL обеспечивает строгую целостность данных для критичных бизнес-сущностей, MongoDB оптимальна для частых изменений схемы данных диаграмм и горизонтального масштабирования, Redis обеспечивает хорошее время отклика для операций аутентификации, а S3 дает экономичное хранение больших бинарных объектов с встроенной репликацией.

Последствия

Положительные: Каждое хранилище оптимально для своей задачи, производительность операций с диаграммами повышается на 40-60% по сравнению с единой СУБД.

Отрицательные: Требуется синхронное удаление данных из всех хранилищ при удалении проекта, усложняется резервное копирование.

ADR-005: Архитектура ML-компонентов для генерации диаграмм и AI-помощник

Статус: Принято

Дата: 09.12.2025

Участники: ML-инженер

Контекст

Для выполнения ключевых функций платформы – генерации диаграмм по тексту, работы AI-помощника – требуется интегрировать несколько специализированных ML-моделей. Основные ограничения: время генерации <= 30 секунд, необходимость обработки русскоязычных запросов и работа с графами.

Решение

Использовать каскадную архитектуру из трех моделей, развернутых в собственном Kubernetes-кластере для контроля над задержками и данными. Все модели инкапсулированы в Docker-контейнеры с единым gRPC API.

Модели:

  1. Текст в граф: Fine-tuned InstructBLIP. Модель преобразует русскоязычный текстовый запрос в структурированный JSON-граф. InstructBLIP изначально обучалась на парах “изображение-текст”, что дает ей врожденное понимание пространственных отношений, критичных для диаграмм. GPT-4, будучи чисто текстовой моделью, требует больше данных для обучения этой способности. На GPU A10G инференс занмает 3-5 секунд против 15-20 секунд у более крупных мультимодальных моделей (например, LLaVA-13B). А архитектура FlanT5, на которой построена InstructBLIP, специально оптимизирована для задач следования инструкциям и генерации структурированного вывода (JSON), что критично для преобразования текста в граф.
  2. Граф и компоновка: GNN + Force-Directed алгоритм Для расстановки элементов диаграммы следует использовать кастомную Graph Neural Network (3 слоя Graph Attention). Модель принимает граф и предсказывает начальные координаты узлов, минимизируя будущие пересечения связей. GNN может обрабатывать графы переменного размера без переобучения – критично для диаграмм от 5 до 500 элементов. Трансформеры требуют padding до максимального размера, что неэффективно. GAT использует механизм внимания на ребрах графа, что позволяет модели явно учитывать важность связей. Время инференса GAT растет линейно O(n+e), а не квадратично O(n^2) как у трансформеров.
  3. AI-помощник: CodeLlama-7B с LoRA Модель для контекстных рекомендаций в редакторе основана на CodeLlama-7B-Instruct, дообученной с помощью LoRA на датасете дизайн-рекомендаций. Выбор обусловлен способностью модели понимать структурированные данные и работать в рамках ограничений одной GPU. Модель оптимизирована для работы с длинными контекстами (до 16К), что позволяет передавать полный граф диаграммы (обычно 1-4К токенов) без потери информации. На A10G потребляет 8 gb VRAM против 14 gb у 13B версии, позволяя обслуживать в 1,7 раз больше параллельных запросов. Таким образом, пользовательский запрос обрабатывается последовательно: InstructBLIP создает граф, GNN предлагает компоновку, а потом происходит оценка ее качества. Параллельно CodeLlama анализирует граф и историю действий для выдачи рекомендаций. Ошибка на любом этапе останавливает процесс, экономя вычислительные ресурсы.

Последствия

Положительные: Общее время генерации укладывается в 12-18 секунд, что соответствует требования ТЗ. Архитектура позволяет дообучать компоненты на собранных данных пользователей. Эксплуатационные расходы предсказуемы и контролируемы.

Отрицательные: Значительно возрастает операционная сложность – необходимо поддерживать различные ML-пайплайны, систему мониторинга их работы и регулярное обновление датасетов для дообучения. Требуется выделенная команда из 2+ ML-инженеров.
